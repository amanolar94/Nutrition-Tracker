# Προπονήσεις και ενεργειακό ισοζύγιο

Η λειτουργία επεκτείνει την υπάρχουσα εφαρμογή, βάση και MCP στο `/mcp`.
Δεν αλλάζει λογαριασμούς, OAuth, υπάρχοντα γεύματα ή στόχους διατροφής.

## Ενεργοποίηση στην υπάρχουσα εγκατάσταση

1. Στο **Supabase → SQL Editor**, εκτέλεσε το
   [20261019_workout_energy.sql](../supabase/migrations/20261019_workout_energy.sql).
   Προϋποθέτει τις προηγούμενες migrations, συμπεριλαμβανομένης της
   `20261014_direct_mcp_writes.sql`. Μην επανεκτελέσεις παλαιότερη migration μετά
   τη νέα, γιατί θα αντικαταστήσει την τρέχουσα συνάρτηση εγγραφής.
2. Δημοσίευσε από το ίδιο GitHub repository στο ίδιο Vercel project. Δεν χρειάζεται
   νέο περιβάλλον ή κλειδί. Έλεγξε `/mcp/status`: **3.1.0**, **15 εργαλεία**,
   `dashboard_approval_required: false`. Το status δείχνει τον κώδικα, όχι αν
   εφαρμόστηκε η migration.
3. Στο site: **Ρυθμίσεις → Συντήρηση και ισοζύγιο → Αποθήκευση συντήρησης**.
   Οι **2.000 kcal** που έδωσε ο χρήστης προτείνονται στη φόρμα, αλλά δεν
   εμφανίζονται ως ήδη αποθηκευμένες. Εναλλακτικά, επιβεβαίωσε στο ChatGPT
   «Όρισε τη συντήρησή μου χωρίς προπόνηση στις 2.000 kcal» για `updateEnergySettings`.
4. Ανανέωσε τα εργαλεία της **υπάρχουσας** σύνδεσης Nutrition Tracker στο ChatGPT
   (επανασύνδεση αν χρειάζεται). Ενημέρωσε το υπάρχον skill με τις
   [οδηγίες plugin](plugin-instructions.md). Η έκδοση του πακέτου plugin μπορεί
   να διαφέρει από την έκδοση MCP· δεν δημιουργούμε δεύτερο plugin.

Χωρίς τη νέα migration το site διατηρεί γεύματα, macros, βάρος και στόχους. Οι
νέες καταγραφές προπόνησης και η ρύθμιση συντήρησης παραμένουν ανενεργές.
Τα υπάρχοντα MCP reads γευμάτων/στόχων συνεχίζουν να λειτουργούν· οι συνόψεις
επιστρέφουν `energy_balance.setup_required: true` όσο εκκρεμεί η νέα migration.

## Υπολογισμός

**Ισοζύγιο = φαγητό − (συντήρηση χωρίς προπόνηση + ενεργές θερμίδες προπόνησης)**.

Παράδειγμα: φαγητό 2.200, συντήρηση 2.000, προπόνηση 500 → **−300 kcal**, εκτιμώμενο
έλλειμμα 300 kcal. Θετικό αποτέλεσμα σημαίνει εκτιμώμενο πλεόνασμα.

- Συντήρηση: εκτιμώμενη δαπάνη με τις συνηθισμένες καθημερινές δραστηριότητες,
  χωρίς την καταγεγραμμένη προπόνηση. Δεν είναι βασικός μεταβολισμός (BMR).
- Οι στόχοι φαγητού ανάπαυσης/προπόνησης παραμένουν ανεξάρτητοι. Δεν αποτελούν
  αυτόματα τη συντήρηση και δεν προστίθενται στον υπολογισμό καύσεων.
- Από ρολόι καταχωρίζονται **ενεργές** θερμίδες άσκησης, χωρίς θερμίδες ηρεμίας.
  Πολλές προπονήσεις την ίδια ημέρα αθροίζονται. Αποφεύγονται διπλές καταγραφές
  της ίδιας δραστηριότητας από διαφορετικές συσκευές.
- Gels/ποτά/φαγητό προπόνησης παραμένουν στην πρόσληψη, μία φορά.
- Το ημερήσιο αποτέλεσμα είναι εκτίμηση με όσα έχουν καταγραφεί μέχρι τώρα.
  Δεν επιβεβαιώνει ότι έχουν καταγραφεί όλα τα γεύματα/προπονήσεις.
- Χωρίς συντήρηση, χωρίς γεύματα ή σε μελλοντική ημερομηνία, το ισοζύγιο είναι
  `null`, όχι πλασματικό έλλειμμα. Η εβδομάδα περιλαμβάνει μόνο ημέρες έως σήμερα
  με γεύματα και συντήρηση, εμφανίζει κάλυψη π.χ. **3/7** και εξαιρεί τις υπόλοιπες.
- Τα συνολικά kcal προπονήσεων εβδομάδας περιλαμβάνουν και ημέρες χωρίς γεύματα.
  Οι καύσεις που χρησιμοποιούνται στο ισοζύγιο αφορούν μόνο τις ημέρες σύγκρισης.
- Η τρέχουσα συντήρηση εφαρμόζεται σε όλες τις ημερομηνίες. Αλλαγή της
  επανυπολογίζει προηγούμενα αποτελέσματα· δεν αποθηκεύονται ιστορικά snapshots.
- Η εβδομάδα είναι Δευτέρα–Κυριακή, ημερολόγιο **Europe/Athens** με θερινή ώρα.

## Νέα εργαλεία MCP

Όλα τα αντικείμενα είναι strict. `request_id`/`workout_id`: UUID, `date`: πραγματική
ημερομηνία `YYYY-MM-DD`. Αναλυτικά JSON schemas: [mcp-tools.json](mcp-tools.json).

| Εργαλείο | Παράμετροι |
| --- | --- |
| `addWorkout` | `request_id`, `date`, `name` (1–120 χαρακτήρες), `calories_burned` (>0, ≤20.000 kcal) |
| `getWorkouts` | `date` ή `start_date` + `end_date` (έως 366 ημέρες, 1.000 εγγραφές) |
| `updateWorkout` | `request_id`, `workout_id`, πλήρη `date`, `name`, `calories_burned` |
| `deleteWorkout` | `request_id`, `workout_id` |
| `updateEnergySettings` | `request_id`, `maintenance_calories` (500–10.000 kcal ή `null` για αφαίρεση) |

Το `getNutritionTargets` επιστρέφει επιπλέον `energy_settings.maintenance_calories`.
Τα `getDailySummary`/`getWeeklySummary` διατηρούν τα υπάρχοντα macros και προσθέτουν
`energy_balance`. Αρνητικό `balance_calories` = έλλειμμα. Στην εβδομάδα επιστρέφονται
`included_days`, `included_dates`, `excluded_dates`, `is_partial_week`,
`workout_calories`, `included_workout_calories` και μέσο ισοζύγιο **ανά ημέρα σύγκρισης**.

Οι εγγραφές χρειάζονται OAuth και ρητή επιβεβαίωση στο ChatGPT, χωρίς έγκριση
στο site. Οι ενδείξεις host είναι `readOnlyHint:false`, `destructiveHint:true`,
`idempotentHint:true`. Ο server ελέγχει ταυτότητα/ιδιοκτησία/τιμές/request_id·
η επιβεβαίωση της συνομιλίας επιβάλλεται από host και οδηγίες plugin.

Οι νέοι πίνακες έχουν RLS και μόνο SELECT για authenticated χρήστες. Κάθε εγγραφή,
και από browser, περνά από το ίδιο `write_nutrition` RPC. Το journal παραμένει
ιδιωτικό. Ίδιο request_id + ίδιο περιεχόμενο επιστρέφει το αρχικό αποτέλεσμα·
αλλαγή περιεχομένου απορρίπτεται. Κάθε νέα διόρθωση/διαγραφή παίρνει νέο UUID.

## Έλεγχοι

`npm test`, `npm run build`, `npm run test:browser`.

Ελέγχονται πραγματικό PostgreSQL μέσω PGlite, official MCP SDK μέσω Streamable
HTTP και Chromium με τοπική προσομοίωση του Supabase HTTP bridge: ανάλυση χωρίς
εγγραφή, άμεση εγγραφή μετά από κλήση, επανάληψη, ανάγνωση, διόρθωση, διαγραφή,
δύο χρήστες, απόρριψη anonymous, κάλυψη εβδομάδας, μηδενική διπλομέτρηση fueling,
εμφάνιση MCP εγγραφής στο dashboard και retry μετά από χαμένη απάντηση.
Ο browser ελέγχεται σε πλάτη 320/375/390/768/1280 px και πριν από τη migration.
Το ιστορικό φορτώνεται σε σελίδες, ώστε το συνηθισμένο όριο 1.000 εγγραφών του
PostgREST να μην αποκρύπτει δεδομένα από το dashboard. Τα εργαλεία MCP ανιχνεύουν
υπέρβαση 1.000 εγγραφών και ζητούν στενότερο εύρος ημερομηνιών.

Αυτά δεν επαληθεύουν live Vercel/Supabase OAuth ή πραγματική επιβεβαίωση του
ChatGPT host. Μετά την ενεργοποίηση, επιβεβαίωσε σε test account συντήρηση 2.000,
φαγητό 2.200 και προπόνηση 500: daily/weekly balance −300 και μία μόνο εγγραφή
μετά από retry. Έλεγξε διορθώσεις/διαγραφή, dashboard και απομόνωση δεύτερου χρήστη.
